# Argo CD and Flux

`--app` takes an Argo CD `Application` or a Flux `HelmRelease`, detected by `kind`. `scan` and `diff` find both kinds in a directory.

| | Argo CD | Flux |
|---|---|---|
| Manifest | `Application`, single or multi-source; every Application in a file is read, as in an app-of-apps file | `HelmRelease` (`helm.toolkit.fluxcd.io/v2`) |
| Chart | `repoURL` + `chart` + `targetRevision`, or a local `path` | `chart.spec.sourceRef` → `HelmRepository` (HTTP or OCI), `GitRepository` in the same repo; `chartRef` → `OCIRepository` or `HelmChart`. Semver ranges (`>=1.0.0`, `1.x`) are resolved |
| Values | `valueFiles` (`$values/` refs), `values`, `valuesObject`, `parameters` | `valuesFrom` ConfigMaps/Secrets (manifests or `configMapGenerator`, `targetPath`, `optional`), then `spec.values` |
| Overlays | — | A directory with a `kustomization.yaml` is built in process (the same kustomize library Flux uses), so patches are applied; the `components` of the Flux `Kustomization` whose `spec.path` is that directory are added, as Flux does; each key still points to the file and line that set it |
| Not read | `ApplicationSet` | the values of SOPS-encrypted Secrets and of sources not in the repository (reported as a note, see `valuesFrom` below), charts from other git repositories, `chart.spec.valuesFiles` (reported as a note), `${var}` you do not define (left as text) |

## Argo CD Applications

| Field | How it is read |
|---|---|
| `sources` with `ref: values` + `$values/path` | `$values` is the root of the local checkout: the git top level, or `--repo-root` |
| `helm.valueFiles` without `$ref/` | relative to the `path` of a local chart; with a remote chart it is an error, only `$ref/` paths are supported |
| `helm.values`, `helm.valuesObject` | used as values |
| `helm.parameters` | applied on top, like `--set` |
| `helm.releaseName` | the release name |
| `helm.ignoreMissingValueFiles` | a missing value file is skipped instead of failing |
| Several `valueFiles` | merged in Argo's order; each key is reported with its source file |
| A source with `path` and no `chart` | the local chart in the repository |
| Several Applications in one file | each one is read; one with no Helm source (plain manifests) is skipped |

## Flux HelmReleases

| Field | How it is read |
|---|---|
| `chart.spec.sourceRef` → `HelmRepository` | found by name in the repository; `spec.url` (`type: oci` means OCI) |
| `chart.spec.sourceRef` → `GitRepository` | if it is this repository, `chart` is a local path; another git repository is an error |
| `chartRef` → `OCIRepository` | `spec.url` + `spec.ref.tag` or `spec.ref.semver`; a digest alone is an error, a tag or range is needed |
| `chartRef` → `HelmChart` | followed to its `HelmRepository` |
| `version` with a range (`>=1.0.0`, `1.x`) | HTTP: picked from `index.yaml`; OCI: the highest tag that satisfies it |
| `valuesFrom` ConfigMap | a manifest in the repository (`data`), or one generated by `configMapGenerator`, read from its source file |
| `valuesFrom` Secret | read if it is plain text; a `sops:` block is handled like a source not in the repository |
| `valuesFrom` not in the repository | a Secret created on the cluster (by an ExternalSecret, for instance) or SOPS-encrypted: with `targetPath`, the path gets a placeholder where the chart has no default, so the chart renders as on the cluster; without `targetPath`, the source is skipped. Both are reported as a note |
| `valuesFrom[].targetPath` | the value goes to that path, like `--set` |
| `valuesFrom[].optional` | missing and optional: ignored, like the helm-controller does |
| Merge order | `valuesFrom` in list order, then `spec.values` on top, as the helm-controller does |
| Release name | `spec.releaseName`; otherwise `<targetNamespace>-<name>` when there is a `targetNamespace`; otherwise the name |
| Namespace | `spec.targetNamespace`, otherwise the `targetNamespace` of the Flux `Kustomization` that applies the directory, otherwise `metadata.namespace`, otherwise `default` |

The Flux `Kustomization` is the one whose `spec.path` is the HelmRelease's directory, or the closest directory above it.

YAML anchors and aliases (`name: &app web`, then `targetNamespace: *namespace` or `APP: *app`) are followed in every field of HelmReleases, Kustomizations and sources, as Flux reads them.

A HelmRelease is shown as `<namespace>/<name>`. When several sources or ConfigMaps have the same name, a ConfigMap from a `configMapGenerator` wins, then an object in the same namespace, then the one whose directory shares the longest prefix with the HelmRelease (`clusters/staging` versus `clusters/production`).

## Kustomize overlays

Flux repositories usually keep the HelmRelease in `apps/base/` and patch the version and values per environment. Reading only the base file would give the wrong result, so a directory with a `kustomization.yaml` is built first:

| Mode | When | What is read |
|---|---|---|
| File | `check --app release.yaml`, or a directory without `kustomization.yaml` | the HelmRelease as it is in the file |
| Build | a directory with `kustomization.yaml` (e.g. `scan apps/production`) | the result of `kustomize build`, with the patches applied |

```bash
deadvalues scan apps
```

```
APP                         CHART            DEAD   COND  REDUNDANT  ALIVE
production:podinfo/podinfo  podinfo 6.15.0      0      0          0      7
staging:podinfo/podinfo     podinfo 6.15.0      0      0          0      7
```

`scan` finds the overlays to build on its own (kustomize directories no other kustomization includes). A kustomize `Component` (`kind: Component`) is never built on its own, since it only makes sense inside what includes it: it is read through the overlay or the Flux `Kustomization` that lists it, with that app's namespace and variables. Point `scan` at the component's own directory to build it anyway. The Flux `Kustomization` objects in `clusters/<name>` are not followed: point `scan` at the app directories (`apps/production`, `infrastructure/controllers`).

## Flux variables

`${var}` placeholders get the `postBuild` variables of the Flux `Kustomization` that applies the directory, as on the cluster: `substituteFrom` ConfigMaps and Secrets found in the repository, then `substitute` on top. A source that is not in the repository, or is SOPS-encrypted, is reported as a note and its variables stay as `${var}` text; an `optional` one is skipped.

Values in `.deadvalues.yaml` win over both, and cover variables a parent `Kustomization` injects into its children with `patches`, which are not followed:

```yaml
flux:
  substitute:
    cluster_domain: example.com
```
